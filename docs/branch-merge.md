# 브랜치 동기화 · 머지 관리 설계

> 상태: **설계안 (구현 전 확인용)**. 이 문서가 확정되면 `src/sync/`의 자동 머지(`mergePush`)·머지 확인 창·머지 백업을 이 구조로 바꾼다.

## 0. 목표와 원칙

혼자 쓰는 앱이지만 패드·컴퓨터를 자주 오간다. 지금은 올리기 때 자동 3-way 머지가 일어나고, 겹치면 "원격 우선 / 이 기기 우선"을 한 번에 고른다. 이를 **git 브랜치처럼** 바꾼다.

1. **기기마다 자기 파일(브랜치)에만 쓴다.** 한 파일을 두 기기가 덮어쓰는 일이 없으므로, 한 기기의 업로드가 다른 기기의 업로드를 지워 버리는 일(lost update)이 구조적으로 없다.
2. **머지는 사용자가 '머지 관리'에서 직접 확인하고 누른다.** 자동 머지는 없다.
3. **머지에는 삭제가 없다.** 한 기기에서 지운 획도 다른 기기에 남아 있으면 기본으로 살린다. 지운 획은 별도 레이어로 보여 주고, 사용자가 고른 것만 버린다.
4. **한쪽만 바뀌었으면 자동으로 따라간다(fast-forward).** 머지 관리에는 양쪽이 모두 바뀐 노트만 올라온다.
5. **네트워크는 지금처럼 사용자가 누를 때만 쓴다.** "자동 동기화 없음" 규칙(`tools/e2e/stores.ts`)은 그대로다.
6. **머지 화면은 패드(펜·손가락)와 컴퓨터(마우스·키보드)에서 똑같이 쓸 수 있어야 한다.**
7. **보관물은 눈에 보이고 정리할 수 있어야 한다.** 자동 고정(keepForever)은 하지 않는다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| **main** | 합쳐진 결과. 받기는 main을 받는다. 노트마다 1개 |
| **브랜치** | 기기 하나가 올린 그 노트의 상태. 노트 × 기기마다 1개. 그 기기만 쓴다 |
| **세대(gen)** | main이 바뀔 때마다 1씩 오르는 번호 |
| **출발점(base)** | 이 기기가 마지막으로 맞춘 main의 세대와 그때의 내용(이 기기 로컬에 보관) |
| **변화 목록(delta)** | 브랜치가 출발점에서 무엇을 추가·삭제·수정했는지. 브랜치 파일에 함께 실린다 |
| **fast-forward** | 한쪽만 바뀌어서 머지 없이 그대로 따라가는 것 |
| **머지 작업본** | 머지 화면에서 고른 것·옮긴 것·지운 것. 최종 머지 전까지 이 기기에 저장된다 |

## 2. Drive 구조

```
Inkpad/
  docs/{docId}.json                 ← main (지금 파일 그대로 — 형식에 필드가 늘어난다)
  branches/{docId}@{deviceId}.json  ← 기기 브랜치 (그 기기만 쓴다)
  assets/{sha256}.{ext}             ← 원본 (지금과 같음)
  backups/                          ← 옛 머지 백업 (새로 만들지 않음, 보관함 관리에서 정리)
```

- `branches/`는 한 폴더에 평평하게 두고 `appProperties`(`docId`, `deviceId`, `device`, `seq`, `baseGen`, `updatedAt`)로 찾는다. 목록 요청 1번으로 모든 브랜치 상태를 알 수 있다.
- **기기 ID(`deviceId`)** 는 처음 한 번 만드는 ULID로, 바꿀 수 있는 기기 이름(`deviceName`)과 별개다. 이름을 바꿔도 브랜치는 같다.

### 2.1 main 파일에 더해지는 것

```ts
interface MainFile extends DocFileV1 {
  gen: number
  /** 이 main에 반영된 브랜치 — 기기별로 몇 번째 업로드(seq)까지 들어 있는가 */
  merged: Record<DeviceId, number>
  /** 이 세대를 만든 동작 — 'ff'(따라가기) | 'merge'(최종 머지) | 'restore'(되돌리기) */
  made: { kind: 'ff' | 'merge' | 'restore'; deviceId: DeviceId; at: number }
}
```

### 2.2 브랜치 파일

```ts
interface BranchFile extends DocFileV1 {
  deviceId: DeviceId
  seq: number          // 이 기기가 이 노트 브랜치를 올린 횟수 (1, 2, 3 …)
  baseGen: number      // 출발점 main 세대
  delta: Delta         // 출발점 대비 변화
}

interface Delta {
  added: ID[]                                  // 새로 그린 획·요소·페이지·블록
  removed: ID[]                                // 지운 것
  modified: { id: ID; baseHash: string }[]     // 고친 것 + 고치기 전 내용의 해시
  split: { from: ID; pieces: ID[] }[]          // 부분 지우개: 원래 획 → 남은 조각
  meta: Partial<Record<'title' | 'category' | 'pageOrder' | 'mode', true>>  // 바꾼 문서 정보
}
```

- 브랜치는 **전체 내용 + 변화 목록**을 함께 싣는다. 머지하는 기기는 그 브랜치의 출발점 내용이 없어도 변화 목록만으로 "새로 그림 / 지움 / 고침"을 구분할 수 있다. 옛 main 리비전을 내려받을 필요가 없으므로 고정(keepForever)도 필요 없다.
- `baseHash`는 고치기 전 요소의 짧은 해시다. main의 그 요소가 이 해시와 다르면 "양쪽에서 고침"이다.
- **부분 지우개 계보(`split`)**: 지금 엔진은 부분 지우개로 잘린 조각에 새 ID를 주고 원래 획을 지운다(`src/engine/engine.ts`의 `eraseAt`). 조각에 `splitFrom`을 기록해 두면, 머지가 "원래 획 삭제 + 새 획 2개"가 아니라 "그 획의 부분 지움" 하나로 다룰 수 있다.

## 3. 동작

### 3.1 상태 판정 (노트 하나, 이 기기 기준)

| 이 기기에 올리지 않은 변경 | main이 내 출발점 이후 바뀜 | 상태 | 하는 일 |
|---|---|---|---|
| 없음 | 아니오 | 최신 | — |
| 없음 | 예 | 받을 것 | 받기 = main으로 따라가기 |
| 있음 | 아니오 | 올릴 것 | 올리기 = 브랜치 업로드 → main 따라가기(ff) |
| 있음 | 예 | **갈라짐** | 올리기 = 브랜치 업로드만 → **머지 관리**에 올라옴 |

다른 기기의 브랜치가 `seq > main.merged[그 기기]`이고 main으로 따라가지 못한 상태(갈라짐)이면, 이 기기에서도 그 노트가 머지 관리에 보인다. 어느 기기에서든 머지할 수 있다.

### 3.2 올리기

1. 이 기기 브랜치를 올린다(`seq + 1`, 변화 목록 포함). 이 파일은 이 기기만 쓰므로 경합이 없다.
2. main이 내 출발점 세대 그대로면 main을 이 내용으로 바꾼다(ff, `gen + 1`, `merged[나] = seq`). 출발점도 새 main으로 옮긴다.
3. main이 그 사이 바뀌었으면 main은 건드리지 않는다. 노트는 "갈라짐"이 되어 머지 관리에 올라온다.

**main 쓰기 경합은 데이터를 잃지 않는다.** 두 기기가 동시에 2를 해서 한쪽 main 쓰기가 덮이더라도, 진 쪽 내용은 그 기기 브랜치에 그대로 있다. `seq > main.merged[그 기기]`이므로 다음 목록 새로고침에서 머지 관리에 다시 나타난다. main은 브랜치들에서 다시 만들 수 있는 결과물일 뿐이고, 원본은 브랜치들이다. main을 쓰기 직전에 세대를 한 번 더 확인해 경합 창도 좁힌다.

### 3.3 받기

- 올리지 않은 변경이 없는 노트: main을 받아 적용하고 출발점을 옮긴다(지금의 받기와 같음).
- 올리지 않은 변경이 있는 노트: 받지 않고 "갈라짐(올리기 필요)"으로 표시한다. 지금처럼 이유 없이 건너뛰지 않고 목록과 미리보기에 이유를 보여 준다.
- **자기 브랜치 이어 쓰기(자동 재정렬)**: 내가 올린 브랜치가 이미 main에 반영됐고(`merged[나] ≥ 내 seq`), 그 뒤 내가 고친 획들을 main에서 아무도 건드리지 않았으면, 내 새 변경을 새 main 위에 자동으로 얹는다. 겹치는 획이 하나라도 있으면 자동으로 하지 않고 "갈라짐"으로 둔다. (§9 열린 질문 1)

### 3.4 머지 관리 (목록)

설정 > 동기화 옆에 **머지 관리** 화면을 둔다. 라이브러리 상단에는 개수 배지를 단다.

- 행 하나 = 갈라진 노트 하나: 제목, 관련 기기들(예: `iPad · 15:20 / PC · 16:02`), 변화 요약(`새 획 +34 · 지운 획 5 · 양쪽 고침 1`).
- 행을 누르면 **머지 화면**을 연다.
- 작업본이 있는 노트는 "작업 중" 표시를 단다.

## 4. 머지 분류 규칙

입력은 현재 main(M)과, 머지할 브랜치들(B₁…Bₙ)의 내용 + 변화 목록이다. 기기가 3대 이상이어도 같은 규칙을 쓴다.

| 분류(레이어) | 판정 | 기본 처리 |
|---|---|---|
| **공통** | M에 있고 어느 브랜치의 변화 목록에도 없는 것 | 유지 |
| **[기기] 새로 그림** | Bᵢ.added에 있고 M에 없음 | **반영** |
| **[기기] 고침** | Bᵢ.modified에 있고, M의 그 요소 해시 = baseHash | **반영** (원래대로 되돌리기 선택 가능) |
| **[기기] 지움** | Bᵢ.removed 또는 Bᵢ.split에 있고 M에 아직 있음 | **유지(삭제 안 함)**. "이 지움 반영"을 고르면 지움 / 조각으로 바꿈 |
| **양쪽 고침** | 같은 요소를 둘 이상의 브랜치가 고쳤거나, M의 해시 ≠ baseHash | 하나를 고를 때까지 최종 머지 불가 (기본 선택 = 가장 최근 것) |
| (자동 정리) | Bᵢ에 있고 M에 같은 내용으로 이미 있음 | 공통으로 본다 (이미 머지된 것) |
| (자동 정리) | 이전 머지에서 버린 것이 Bᵢ에 출발점부터 그대로 남아 있음 | 다시 올라오지 않는다 (변화 목록에 없으므로) |

- **부분 지움의 기본값**: 원래 획을 유지하고 조각은 숨긴다. 조각은 원래 획의 일부라서, 둘 다 살리면 선만 이중으로 겹친다. "지움 반영"을 고르면 원래 획을 조각으로 바꾼다. 두 기기가 같은 획을 각각 부분 지운 경우, 1차 구현에서는 한 기기의 지움만 반영할 수 있다(§9 열린 질문 3).
- **페이지**: 새 페이지는 그 브랜치의 페이지 순서에서 바로 앞 페이지 뒤에 끼운다. 지운 페이지는 '지움' 레이어(기본 유지)에 넣는다. 속지·크기 변경은 한쪽만 바꿨으면 반영하고, 양쪽이면 '양쪽 고침'이다.
- **제목·카테고리·모드**: 한쪽만 바꿨으면 반영하고, 양쪽이면 머지 화면 상단에서 고른다.
- **블록(메모 등)**: 획과 같은 규칙이다. 지금 코드의 `updatedAt` 비교는 쓰지 않는다.
- **원본(PDF·이미지)**: 합집합이다.

## 5. 머지 화면 (패드·컴퓨터 공용)

지금 편집기 엔진을 **머지 모드**로 연다. 그려지는 것은 "M + 반영된 변화"이고, 머지 화면에서 한 편집은 작업본에만 쌓인다.

### 5.1 화면 구성

```
┌───────────────────────────────────────────────┬──────────────────────┐
│ ← 머지: 물리 노트          [결과 미리보기]  ⟲ ⟳ │ 레이어                │
│                                                 │ ● 공통          1,204 │
│                                                 │ ─ iPad ──────────────│
│               (캔버스)                           │ ◉ 새로 그림   +34 [반영]│
│                                                 │ ○ 지움          5 [유지]│
│                                                 │ ─ PC ────────────────│
│                                                 │ ◉ 새로 그림   +12 [반영]│
│                                                 │ ⚠ 양쪽 고침     1 [선택]│
│                                                 │                      │
│ [올가미] [지우개] [반영] [버리기]   ◀ 변경 3/9 ▶ │ [나중에]  [최종 머지] │
└───────────────────────────────────────────────┴──────────────────────┘
```

- 폭이 900px 이상이면 레이어를 오른쪽 패널로, 좁으면(패드 세로·작은 창) 아래쪽 시트로 둔다. 같은 컴포넌트다.
- 모든 버튼은 손가락으로 누를 수 있게 44px 이상으로 한다.

### 5.2 레이어 보기

- 획 색은 바꾸지 않는다. 노트 자체가 여러 색이라 색을 입히면 헷갈린다. 대신:
  - **선택한 레이어**는 원래대로, 나머지는 흐리게(약 25%) 그린다.
  - 기기마다 정해진 표시 색으로 **획 둘레에 얇은 테두리**를 그린다(켜고 끌 수 있음).
  - '지움' 레이어 획은 점선이나 반투명으로, '버린' 항목은 결과 미리보기에서 사라진다.
- 레이어 행: 눈 아이콘(보이기/숨기기), "이 레이어만 보기", 개수, 반영/유지/버리기 일괄 버튼.
- **◀ 변경 n/N ▶**: 다음 변경이 있는 곳으로 화면을 옮긴다(페이지 넘김 + 확대).

### 5.3 도구 (선택한 레이어에만 적용)

| 도구 | 동작 |
|---|---|
| 올가미 | 선택한 레이어의 획만 고른다 → 끌어 옮기기, 반영, 버리기, 다른 기기 버전으로 바꾸기 |
| 지우개 | 선택한 레이어의 획만 지운다(획 단위·부분 모두). 예: "PC 레이어의 이 부분만 지우기" |
| 반영 / 버리기 | 올가미로 고른 것, 또는 탭한 획 하나에 적용 |
| 되돌리기 / 다시 | 머지 화면 안의 작업만 되돌린다 |

- 1차 구현에서 머지 화면에서는 새로 그리지 않는다. 펜은 없다(§9 열린 질문 2).
- **입력**:
  - 패드: 펜 = 도구, 손가락 = 이동·확대(지금 편집기와 같음), 두 손가락 탭 = 되돌리기
  - 컴퓨터: 마우스 = 도구, 휠·트랙패드 = 이동·확대, 스페이스 + 끌기 = 이동
  - 단축키: `1`–`9` 레이어 선택, `H` 숨기기, `L` 올가미, `E` 지우개, `Enter` 반영, `Backspace` 버리기, `⌘Z`/`⇧⌘Z`, `]`/`[` 다음/이전 변경

### 5.4 작업본과 최종 머지

- 모든 선택과 편집은 **머지 작업본**(IndexedDB `mergeDrafts`)에 바로 저장된다. 앱이 꺼져도 이어서 할 수 있다. "나중에"는 작업본을 둔 채 닫는다.
- 작업본은 입력들의 버전(main 세대, 브랜치별 seq)을 기억한다. 다시 열었는데 입력이 바뀌었으면(다른 기기가 또 올림) 알리고, 고른 내용을 ID 기준으로 새 입력에 다시 적용한다.
- **최종 머지**를 누르면:
  1. 결과 내용을 만들고, '양쪽 고침'이 모두 골라졌는지 확인한다.
  2. 이 기기에 덮이기 전 상태를 **로컬 스냅샷**으로 남긴다(§6).
  3. main을 쓴다: `gen + 1`, `merged`에 반영한 모든 브랜치의 seq, `made.kind = 'merge'`. 쓰기 직전 세대를 다시 확인하고, 그 사이 바뀌었으면 작업본을 새 main 위에 다시 적용해 한 번 더 보여 준다.
  4. 이 기기에 적용하고 출발점을 옮긴다. 다른 기기는 다음 받기 때 따라온다(그 기기 브랜치가 이미 반영됐으므로 ff).

## 6. 버전 기록과 보관함 관리

| 무엇 | 어디 | 정리 |
|---|---|---|
| main 세대 | `docs/{docId}.json`의 Drive 리비전 | Drive가 30일 뒤 자동 정리. 사용자가 직접 고정한 것만 남는다 |
| 기기 브랜치 | `branches/…` 파일 (그 리비전 = 그 기기의 업로드 기록) | 보관함 관리에서 브랜치 삭제 |
| 로컬 스냅샷 | 이 기기 IndexedDB | 노트당 최근 20개 + 전체 용량 상한(기본 200MB). 넘으면 오래된 것부터 지운다 |
| 옛 머지 백업 | `backups/` | 새로 만들지 않는다. 보관함 관리에서 일괄 정리 |

- **로컬 스냅샷**은 이 기기 내용이 덮이기 직전(받기, 따라가기, 최종 머지, 되돌리기)에 자동으로 남는다. 네트워크 없이 되돌릴 수 있는 안전망이다.
- **자동 고정은 없다.** 되돌리기 때 리비전을 고정하던 동작(`revisions.ts`의 `restoreDocRevision`, `sync.ts`의 되돌림 업로드)을 없앤다. 고정은 사용자가 버전 기록에서 직접 누른 것만 한다.
  - ⚠️ 확인할 것: 코드는 "고정한 리비전만 내려받을 수 있다"고 가정한다. 실제 Drive에서 고정 없이 내려받을 수 있는지 한 번 실험한다. 안 된다면, 고정하지 않은 리비전 되돌리기는 "고정 1칸을 쓴다"고 알리고, 그 고정에 '되돌리기용' 표식을 달아 정리 대상으로 보여 준다.
- **보관함 관리 화면** (설정 > 동기화 > 보관함):
  - 노트별: 브랜치(기기·마지막 업로드·머지됨/안 됨), 고정 수(n/200), 로컬 스냅샷 수·용량, 옛 백업 수·용량
  - 일괄 정리:
    - 머지 끝난 브랜치 지우기 (머지 안 된 브랜치는 경고 후에만)
    - 쓰지 않는 기기의 브랜치 지우기: 기기 목록에서 기기를 '퇴역' 처리하면 그 기기 브랜치를 한 번에 정리
    - 오래된 로컬 스냅샷 지우기
    - 옛 머지 백업 모두 지우기
    - 클라우드에서 지운 노트의 남은 파일 지우기
- **버전 기록 패널**은 한 목록에 main 세대(따라가기·머지·되돌리기 표시), 기기별 브랜치 업로드, 로컬 스냅샷을 시간순으로 보여 준다. 되돌리기 전에 미리보기(썸네일 + `획 +12 / −3` 요약)를 보여 준다.
- **되돌리기**는 그 내용을 이 기기에 적용하고 "올리지 않은 변경"으로 만든다. 그다음은 보통의 올리기 흐름(브랜치 → ff 또는 머지 관리)을 탄다.

## 8. 구현 단계

| 단계 | 내용 | 테스트 |
|---|---|---|

## 9. 결정 사항과 열린 질문

**확정**

- 지운 획은 별도 레이어로 보여 주고, 기본은 살린다.
- 한쪽만 바뀌었으면 자동으로 따라간다(fast-forward).
- 머지 화면은 패드·컴퓨터 공용이다.
- 저장소는 Google Drive를 유지하고, 동기화는 수동을 유지한다.

**열린 질문** (정해지기 전까지는 괄호 안 기본값으로 진행)

1. **자기 브랜치 이어 쓰기(§3.3)를 자동으로 할까?** 내 변경이 이미 머지된 뒤 이어서 그린 것을, 겹치는 획이 없을 때 자동으로 새 main 위에 얹을지. (기본: 자동. 겹치면 머지 관리로 보낸다)
2. **머지 화면에서 새로 그리기를 허용할까?** (기본: 1차 구현에서는 허용하지 않음)
3. **두 기기가 같은 획을 각각 부분 지운 경우**: 둘 다 반영하려면 남은 부분의 교집합을 계산해야 한다. (기본: 1차 구현에서는 한 기기의 지움만 반영할 수 있다고 안내)
4. **기기 표시 색**: 자동 배정(기본) 또는 기기 설정에서 직접 고르기.
